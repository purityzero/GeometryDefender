## 미완료 작업 보고 (세션 시작 시)
- 세션에서 처음 호출되면, 가장 먼저 `.claude/UNFINISHED.md`를 확인해 끝내지 못한 작업이 있으면 첫 응답에서 사용자에게 알려준다.
- 작업이 미완료 상태로 세션이 끝날 것 같으면(중단 요청, 검증 못 함 등) `.claude/UNFINISHED.md`에 날짜, 남은 작업, 관련 파일을 기록해 둔다.
- 미완료 작업을 마저 끝내면 해당 항목을 `.claude/UNFINISHED.md`에서 제거한다.

## 공동 md 파일 생성 규칙
- 리비전 및 날짜 별로 개요, 파일, 증상, 원인, 수정을 명확히 기록한다.
- 형상관리의 리비전을 알 수 없을 경우 무시하여도 된다.
- 같은 날짜가 있으면 0부터의 숫자를 기록한다. 
예시) 2026-07-12-0, 2026-07-12-1

### md 파일 읽기/생성/갱신 (자동)
- 클래스(.cs)나 프리팹(.prefab)을 수정하기 전에, 대응하는 md 파일이 있는지 반드시 먼저 확인한다.
  - .claude/class/{클래스명}.md, .claude/prefab/{프리팹명}.md
- md 파일이 있으면: 읽고 나서 작업을 시작한다. 코드보다 md의 기록이 오래됐을 수 있으므로, 실제 코드/프리팹과 다른 내용을 발견하면 md를 실제 상태 기준으로 정정한다.
- md 파일이 없으면: 작업 완료 후 위 생성 규칙에 따라 새로 생성한다. 저장 폴더(.claude/class, .claude/prefab)가 없으면 폴더부터 생성한다.
- 주의: 기록용 md는 .claude/rules/ 안에 두지 않는다 — rules 폴더의 md는 매 세션 자동 로드되어 컨텍스트를 낭비한다.
- 작업을 완료하면 해당 md 파일에 이번 작업 내역(공통 규칙의 날짜별 항목)을 추가하고, 계층 구조·직렬화 필드 등 현재 상태 정보가 바뀌었으면 함께 갱신한다.
- md 읽기/생성/갱신은 사용자가 요청하지 않아도 항상 수행한다. 단, 코드를 읽기만 한 경우(수정 없음)에는 md를 갱신하지 않는다.

## class 작업 시 md 파일 생성 규칙
- .claude/class 폴더 안에 {클래스명}.md 파일로 저장한다.
예시) .claude/class/{클래스명}.md
- 수정한 코드 전, 후를 기록해 둔다. (함수단위)
- 연관된 클래스는 맨 위 상단에 스크립트 명만 저장해둔다.

## prefab 작업 시 md 파일 생성 규칙
- .claude/prefab 폴더 안에 {프리팹명}.md 파일로 저장한다.
예시) .claude/prefab/{프리팹명}.md
- 프리팹 계층 구조를 트리 형태로 기록해 둔다. (각 오브젝트에 핵심 컴포넌트 병기)
- 수정한 컴포넌트/필드는 전, 후를 기록해 둔다. (오브젝트 단위)
- 스크립트가 참조하는 오브젝트는 fileID를 함께 기록해 둔다.
- 연관된 스크립트와 중첩(nested) 프리팹은 맨 위 상단에 이름만 저장해둔다.


## 코드 규칙
- 기본 규칙은 루트 CODE.md를 따른다.
- 특정 폴더/시스템 전용 규칙은 .claude/rules/*.md에 paths로 지정되어 있으며, 충돌 시 더 좁은 스코프의 규칙이 우선한다.

## 피드백 관련 된 내용
- 작업 후 한번 더 생각해서 공용으로 사용되면 좋을 것 같은 것은 해당 md 파일에 작성 할 수 있다. 다만, 사용자의 동의를 한번 더 얻은 다음 저장한다.

### 피드백 반영 프로세스 (자가 진단 → 문서 수정)
이 문서는 고정 규칙집이 아니라 계속 갱신되는 살아있는 문서다. 작업 중 지적/정정("아니 그게 아니라", "왜 그렇게 했어", 반대로 "어 그거 맞아 계속 그렇게 해")을 받으면 다음 순서로 처리한다.

1. **자가 진단**: 이 피드백이 —
   - (a) 이번 한 건, 혹은 특정 프로젝트에만 해당하는 지엽적 케이스인지, 아니면
   - (b) 프로젝트에 상관없이 반복될 수 있는 일반 규칙인지 구분한다.
   - (a)면 이 공용 문서는 건드리지 않고 해당 프로젝트의 별도 작업 기록에만 남긴다.
   - (b)면 아래 2번으로 진행한다.
2. **기존 항목과 대조**: 이 문서에 이미 관련 규칙이 있는지 먼저 찾는다.
   - **이미 있는데 이번 피드백이 그 규칙과 어긋나거나 더 정확한 표현이 필요하면** → 새 항목을 추가하지 말고 **기존 문장을 직접 고친다**(추가가 아니라 수정이 기본값). 단정적 문장이 반례를 만났다면 단서 조건을 붙이거나 "상황에 따라 다를 수 있음"으로 완화한다.
   - **없으면** 가장 관련 있는 장 밑에 새 항목으로 추가하거나, 어느 장에도 안 맞으면 새 장을 추가한다.
   - **프로젝트 고유 명사(특정 클래스명·파일명 등)가 섞여 들어가려 하면 일반화한다** — "이런 역할을 하는 것" 수준으로 추상화해서 적을 것. 이 문서는 순수 공용 원칙만 남기는 게 목적이므로, 특정 코드베이스에서만 통하는 이름은 여기 대신 해당 프로젝트의 개별 작업 기록에 남긴다.
3. **근거를 함께 남긴다**: 규칙 문장만 고치지 말고 왜 이렇게 바뀌었는지 한 줄 배경을 남긴다. 근거 없는 규칙은 다음에 왜 있는지 몰라 지켜지지 않거나 잘못 일반화된다.
4. **확정 전 되묻지 않기**: 이미 사용자가 명확히 정정/확인해준 내용이면 "이렇게 반영할까요?"라고 다시 묻지 말고 바로 문서를 고친다. (a)/(b) 판단이 안 서는 경우에만 되묻는다.
5. **문서가 비대해지면 정리**: 같은 주제로 예외 조건이 계속 덧붙어 문장이 길어지면, 그 시점에 항목 전체를 재작성해 압축한다(누더기로 계속 이어붙이지 않는다).

## 코딩보다 생각이 먼저다

**가정하지 않는다. 혼란을 숨기지 않는다. 트레이드오프를 드러낸다.**

구현하기 전에:
- 전제하고 있는 가정을 명시적으로 말한다. 확신이 없으면 묻는다.
- 여러 해석이 가능하면 모두 제시한다. 말없이 하나를 고르지 않는다.
- 더 단순한 접근이 있다면 말한다. 타당하다면 반대 의견도 낸다.
- 불명확한 부분이 있으면 멈춘다. 무엇이 헷갈리는지 명확히 하고 질문한다.

## 단순함을 최우선으로

**문제를 푸는 데 필요한 최소한의 코드만. 추측에 기반한 코드는 금지.**

- 요청받은 것 이상의 기능을 만들지 않는다.
- 한 곳에서만 쓰이는 코드에 추상화를 적용하지 않는다.
- 요청받지 않은 "유연성"이나 "설정 가능성"을 추가하지 않는다.
- 일어날 수 없는 시나리오에 대한 예외 처리를 작성하지 않는다.
- 200줄을 썼는데 50줄로 줄일 수 있다면 다시 작성한다.

자문할 것: "시니어 엔지니어가 보면 과하게 복잡하다고 할까?" 그렇다면 단순화한다.

## 최소 침습 변경

**꼭 필요한 부분만 손댄다. 정리는 내가 어지른 것만 한다.**

기존 코드를 수정할 때:
- 인접한 코드, 주석, 포맷을 마음대로 "개선"하지 않는다.
- 고장 나지 않은 것을 리팩토링하지 않는다.
- 내 취향과 달라도 기존 코드 스타일을 따른다.
- 무관한 죽은 코드를 발견하면 알리기만 하고, 지우지 않는다.

내 변경으로 인해 쓸모없어진 코드가 생겼다면:
- **내 변경 때문에** 미사용이 된 using·변수·함수는 제거한다.
- 원래부터 있던 죽은 코드는 요청이 없는 한 건드리지 않는다.

판단 기준: 변경된 모든 줄이 사용자의 요청으로 직접 설명될 수 있어야 한다.

## 목표 중심으로 실행하기

**성공 기준을 먼저 정의한다. 검증에 통과할 때까지 반복한다.**

작업을 검증 가능한 목표로 변환한다:
- "유효성 검사 추가해줘" → "잘못된 입력에 대한 테스트를 먼저 작성하고, 그것을 통과시킨다"
- "버그 고쳐줘" → "버그를 재현하는 테스트를 작성하고, 그것을 통과시킨다"
- "X 리팩토링해줘" → "리팩토링 전과 후 모두 테스트가 통과하는지 확인한다"

여러 단계가 필요한 작업이라면 간단한 계획부터 제시한다.

1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]

성공 기준이 탄탄하면 혼자서도 루프를 돌며 작업할 수 있다. 기준이 허술하면("일단 되게 해줘") 매번 되물어야 한다.

## 착수 전 체크리스트 (매 작업 공통)

1. **베이스 클래스 확인** — 상속 구조를 먼저 파악한 뒤 올바른 오버라이드 메서드를 사용한다. 커스텀 베이스 클래스(풀링 오브젝트, 리스트 아이템 등)를 상속하는 컴포넌트는 `Awake()`/`Start()`를 그대로 쓰면 안 될 수 있음 — 베이스 클래스가 자체 초기화 훅을 이미 정의해뒀다면 그걸 오버라이드할 것. 이름만 보고 추측하지 말고 베이스 클래스 소스를 직접 열어 확인한다.
2. **외부 시스템 연동이 필요한 기능은 실제 연동 지점부터 확인** — 클라이언트 단독으로 완성할 수 없는 기능(네트워크 요청, 외부 API, 다른 모듈의 인터페이스 등)을 만들기 전에 관련 인터페이스/규격이 이미 정의되어 있는지 먼저 찾는다. 없으면 로그 스텁 + TODO로 표시해두고 UI/로직 골격부터 완성한다(연동은 나중에 이어붙인다). 연동 대상이 서버든, 로컬 세이브 시스템이든, 다른 팀이 만든 모듈이든 동일하게 적용된다.
3. **기존 재사용 후보부터 탐색** — 새 클래스·데이터 구조를 만들기 전에, 기존 구조로 커버되는지 먼저 확인한다(아래 재사용 우선 원칙 참고).
4. **에셋 참조(GUID 등)는 절대 문맥으로 추측하지 않는다** — 반드시 메타/매니페스트 파일을 직접 열어 대조한다. 직렬화 필드가 비어있거나 이름이 비슷하다고 해서 같은 타입이라고 단정하지 말 것 — 실제로 다른 타입을 같은 타입으로 착각해 여러 세션에 걸쳐 잘못 기록된 사례가 있다.

## 재사용 우선 원칙 — 새로 만들기 전에 확인할 것

- **비슷한 개념을 이미 표현할 수 있는 필드/구조가 있다면 그걸 재사용**한다. 새 하위 개념이 기존 enum의 특수값이나 기존 딕셔너리의 확장으로 표현 가능하면, 별도 데이터 클래스를 새로 만들지 않는다.
  - 단, "재사용"이 나중에 서로 다른 갱신 경로가 뒤섞여 데이터가 유실되는 근본 원인이 될 수 있다. 처음엔 재사용하되, 실제로 그런 유실 버그가 발생하면 그때 가서 저장소만 분리(공개 API 시그니처는 유지)하는 2단계 접근이 안전하다.
- **공용 위젯 베이스 클래스 상속으로 중복 로직 제거**: 아이콘+이름+값처럼 여러 화면에서 반복되는 표시 패턴이 있으면, 이미 그 패턴을 캡슐화한 공용 베이스 클래스가 있는지부터 찾는다. 새로 만들기 전에 대상 위젯의 상속 관계를 클래스 선언부에서 직접 확인한다 — 상속 관계를 잘못 짐작해서 "완전히 새 클래스가 필요하다"고 오판하고 구조를 손으로 두 번 만들었다가 되돌린 사례가 있다.
- **공용 헬퍼 함수 재사용**: 텍스트/스프라이트 세팅, 값 변환(스케일 나누기 등)은 프로젝트 공용 확장 메서드/유틸리티로 통일하고, 컴포넌트에 직접 대입하는 코드를 반복 작성하지 않는다. 새 변환 로직을 만들기 전에 프로젝트 내에 이미 흩어져 있는 동일 계열 로직이 없는지 먼저 검색한다.

## 데이터/설정 레이어 — 반복적으로 터지는 버그 유형

### (1) 데이터 파일 컬럼/키 이름 불일치 — 조용히 기본값으로 귀결
많은 데이터 파싱 유틸리티는 존재하지 않는 컬럼/키를 조회해도 에러 없이 기본값(0, 빈 문자열 등)을 반환한다. 즉 코드가 참조하는 필드명과 실제 데이터 파일의 헤더가 다르면, 컴파일도 되고 실행도 되지만 **항상 기본값**이 되어 이상 동작만 남는다(에러 로그조차 없는 경우가 많다).
- **대응**: 특정 조회 결과가 항상 기본값으로만 나올 때는 계산 로직보다 먼저 "코드가 읽는 필드명 == 데이터 파일의 실제 헤더/키"부터 대조한다. 여러 시스템(클라이언트/서버 등)이 같은 데이터 파일을 서로 다른 파서로 읽는 구조라면, 양쪽 필드명이 어긋나 있을 수 있으므로 양쪽 다 확인한다.

### (2) 초기화 로직 중복 호출 → 값이 정확히 N배
데이터 로딩 파이프라인이 "전체 초기화 시점 1회 호출" + "최초 조회 시점에 아직 준비 안 됐으면 재호출"하는 이중 경로를 갖고 있으면, "준비 완료" 플래그 갱신을 빠뜨린 항목은 데이터가 중복 누적되어 값이 정확히 배수로 튀는 버그가 생긴다.
- **대응 패턴**: 초기화 메서드 시작부에 멱등 가드(`if (준비됨) return; 준비됨 = true;`)를 넣는다. 신규 데이터 로더를 만들 때도 처음부터 이 가드를 기본으로 넣는다.

### (3) 비동기 이벤트 처리 후 화면 갱신 호출 누락
외부 응답이든, 다른 시스템의 콜백이든, 비동기로 들어오는 이벤트 핸들러가 내부 데이터는 정상 갱신하면서 이미 화면에 표시 중인 UI를 다시 그리는 호출을 빼먹는 패턴이 여러 도메인에서 반복해서 발견되는 경향이 있다.
- **대응**: 새 이벤트 핸들러를 작성/수정할 때는 "데이터 갱신" + "관련 화면이 열려 있으면 그 화면도 갱신"을 항상 세트로 체크한다.

### (4) 리스트 동기화가 "부분 갱신(merge)"인지 "전체 스냅샷"인지 반드시 확인
외부에서 오는 리스트가 "활성/점유 항목만 담고, 제거된 항목은 리스트에서 아예 빠지는" 방식이라면, 수신 측이 "리스트에 있는 것만 갱신, 없으면 그대로 둔다"는 merge 방식으로 처리할 경우 제거된 항목이 영영 안 지워진다.
- **대응**: 새 리스트 동기화 로직을 짤 때는 적용 전에 대상 영역 전체를 먼저 비운 뒤 리스트를 재적용하는 "전체 스냅샷" 방식을 기본으로 검토한다. 송신 측이 실제로 스냅샷 방식으로 만드는지 먼저 확인한다.

### (5) 여러 개념이 하나의 저장소를 공유할 때 서로 다른 갱신 경로가 서로를 침범
한 저장소(딕셔너리 등)를 두 가지 다른 개념이 같이 쓰면, 한쪽 개념만 갱신하는 로직이 "전체 클리어 후 자기 개념만 다시 채우는" 방식일 경우 다른 개념의 데이터가 유실된다.
- **대응**: 초기엔 공유해도 되지만(위 재사용 우선 원칙 참고), 이런 유실 버그가 실제로 재현되면 저장소를 분리하는 게 근본 해결이다. 임시 백업/복원 패치는 미봉책으로만 취급한다.

## 로컬라이제이션/텍스트 키 관리

- 새 키를 만들기 전에 **완전히 동일한 문구의 공용 키가 이미 있는지 먼저 검색**한다.
- "키 없는 텍스트 컴포넌트 찾기"는 단순 필드 유무 체크가 아니라 다음 세 가지를 함께 판단해야 한다:
  1. 정적 라벨인가, 아니면 런타임에 코드가 매번 값을 덮어쓰는 표시인가(후자는 키 불필요)
  2. 그 UI 요소가 실제로 살아있는 코드 경로인가, 아니면 비활성 상태로 방치된 leftover 목업인가(죽은 UI는 키 스킵)
  3. 원본(마스터) 데이터와 실제 배포되는 사본(클라이언트/서버 등 여러 곳에 복제되는 경우) 전부를 항상 함께 동기화한다.
- 스프레드시트를 스크립트로 직접 편집할 경우, 수식 셀의 **캐시된 계산 결과값은 저장 시 사라질 수 있음**(수식 자체는 보존되어 다시 열면 재계산됨 — 실데이터 손실은 아니지만, 저장 직후 헤드리스 검증 시 빈 값처럼 보여 착각할 수 있으니 주의).

## 권한이 없는 영역과의 협업 경계

이 원칙은 상대 영역이 서버인지, 다른 팀이 만든 모듈인지, 외주/외부 라이브러리인지와 무관하게 동일하게 적용된다.

- 직접 수정할 권한/역할이 아닌 영역의 버그를 발견했을 때는, 원인을 코드 레벨까지 정확히 특정한 뒤 **수정 지점과 근거를 문서로 정리해 담당자에게 전달**하는 것으로 마무리한다. 직접 고치지 않는다.
- 상대 영역이 아직 제공하지 않는 데이터를 자기 쪽에서 우회 계산으로 메꿔야 할 때는, 상대 영역이 나중에 그 데이터를 실제로 제공하기 시작하면 우회 로직을 반드시 제거해야 한다(안 지우면 정식 값 위에 우회 계산이 이중으로 더해지는 회귀 버그가 된다). 우회 로직을 넣을 때 "언제 제거해야 하는가" 조건을 주석/문서에 함께 남겨둔다.
- 다른 영역의 로그를 확인할 때는 그쪽 로깅 파이프라인이 실제로 어디로 출력되는지(콘솔/파일/레벨별 필터링 등) 먼저 확인한다 — 자기 쪽에서 익숙한 로그 함수가 상대 영역 빌드에서는 빈 구현(스텁)일 수 있다.

## 버전 관리 시스템에서 바이너리 자산 병합 주의

- 텍스트 파일(코드, csv 등)의 병합 충돌은 충돌 마커로 명확히 드러나지만, **스프레드시트/이미지 등 바이너리 자산은 병합이 인코딩 손상이나 조용한 데이터 유실로만 나타날 수 있다**(충돌 마커 없음).
- 여러 사람이 "매번 항목만 추가하는" 구조의 파일(enum 정의, 각종 설정 테이블)을 동시에 건드리는 상황에서는, 업데이트/병합 직후 전체 데이터 무결성을 재확인한다 — 병합이 "성공"했다고 표시돼도 실제로는 일부 항목이 사라졌을 수 있다.

## 모호한 요구사항 확인 방식

- 표시값/계산 공식처럼 정답이 여러 갈래로 갈리는 요구사항은, "A로 할까요 B로 할까요" 같은 추상적 질문을 반복하지 말고 **구체적인 예시 숫자/케이스**로 먼저 제시해 확인한다 — 추상적 질문 반복은 왕복 횟수만 늘리고, 원치 않는 방향으로 구현부터 해버리면 반려당하는 비용이 크다.
